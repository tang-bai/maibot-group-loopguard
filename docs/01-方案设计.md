# 多机器人同群防复读插件 · 方案设计

> 目标读者：MaiBot 部署者、插件开发者
> 对应代码：`plugins/maibot-group-loopguard/`（v1.3.0）
> 对照 MaiBot 版本：v1.3.19（commit `c642954`），插件 SDK 2.21.0

---

## 1. 问题定义

### 1.1 现象

同一个 QQ 群里放了两只以上的 MaiBot（或 MaiBot + 其它 LLM 机器人）时，会出现这样的链路：

```
人类：今晚有人开黑吗
 Bot-A：有的有的，我随时可以
 Bot-B：那我也来，几点开始
 Bot-A：那我也来，几点开始？
 Bot-B：那我也来，几点开始？
 ...
```

成因不是"某只机器人坏了"，而是三件事叠加：

1. **每只机器人都把对方当成真人**。消息里没有可靠的 `is_bot` 字段，MaiBot 的入站链路默认所有发送者都是人类。
2. **HeartFlow / Maisaka 是持续观察式的**。普通模式下按"激活度"决定要不要说话，Focus 模式下每几秒观察一次群聊；对方的回复本身就是一个强激活信号。
3. **互相模仿的机制反过来放大了相似度**。表达方式学习、黑话学习会让两只机器人的措辞越来越像，于是第二轮就是"自己的话被对方复述回来"，激活度更高。

### 1.2 代价

| 维度 | 具体损失 |
| --- | --- |
| 成本 | 每轮互激都是一次完整 Planner + Replyer 推理；Focus 模式下 3 秒一轮观察，token 消耗线性上涨 |
| 体验 | 群聊被刷屏，真人被挤走；两只机器人的语气越来越像，反而更假 |
| 记忆 | 复读内容会写进聊天历史与长期记忆，下一轮更容易复读，形成自增强 |
| 运维 | 只能靠人工发现、手动 `/offline` 或停进程，夜里没人看着就一直烧 |

### 1.3 设计目标与非目标

**目标**

- 机器人 → 机器人的消息**不进主链**：不入库、不进上下文、不触发推理（省 token 且不污染记忆）。
- 对"逐字重复 / 抄一遍再补几个字 / 两个账号来回接话 / 短时间爆发"四类形态都能兜住。
- 人类正常聊天完全不受影响；人类插话后机器人立刻恢复正常。
- 误判可观测、可回滚：有演习模式、有命令能看状态、有日志能追责。
- 一只机器人装上也有效；两只都装上效果最好，且不依赖两只之间通信。

**非目标**

- 不做语义级"换个说法"识别（成本与误判都不划算，见 §5.4）。
- 不做跨实例的分布式协调（用 §7 的账号优先级仲裁替代）。
- 主程序源码零改动：全部通过插件系统的 Hook 完成。

## 2. 可行性：插件系统提供了什么

MaiBot 1.3 的插件跑在独立 Runner 子进程里，通过 msgpack RPC 与 Host 通信；Host 在关键执行点触发**命名 Hook**，阻塞模式下插件可以改参甚至 `abort` 整条链路
（[官方 Hook 文档](https://docs.maibot.chat/plugin/hooks)）。逐个核对源码后，可用的闸门如下：

| Hook | 触发位置（源码） | 可 abort | 对本方案的作用 |
| --- | --- | --- | --- |
| `chat.receive.before_process` | `src/chat/message_receive/bot.py:806`，在 `SessionMessage.process()` 之前 | ✅ | **主刹车**：拦下的消息不入库、不建会话、不进 HeartFlow |
| `chat.receive.after_process` | 同上 `:830`，轻量预处理之后 | ✅ | 备用闸门；本方案不用（主刹车更早更省） |
| `send_service.before_send` | `src/services/send_service.py:871`，调 Platform IO 之前 | ✅ | **最后一道闸**：回复已生成、即将外发时再查一次重 |
| `maisaka.planner.before_request` | `src/maisaka/chat_loop_service.py:1255` | ❌（可改参） | 可选软静音：冷却期内摘掉 `reply` 工具定义 |
| `frequency.set_adjust` | 能力调用，落到 `heartflow_manager.adjust_talk_frequency` | — | 可选：冷却期把回复频率倍率压到 0 |

另外两个关键事实来自源码核对：

- `chat.receive.before_process` 的载荷是 `serialize_session_message()` 的结果（`src/plugin_runtime/host/message_utils.py:415`），字段包括
  `platform / account_id / scope / message_info{user_info{user_id,user_nickname,user_cardname}, group_info} / raw_message[组件] / session_id / is_at / is_mentioned`。
  此刻 `processed_plain_text` 尚未生成，文本要从 `raw_message` 里的 `{"type":"text","data":...}` 拼接。
- 插件配置用 `PluginConfigBase` 声明，Runner 首次加载时生成 `config.toml`，WebUI 直接渲染表单；`self.ctx.config.get("bot.qq_account")` 可以读全局 Bot 配置，
  用来识别"本实例自己的账号"。

结论：方案**不需要改主程序**，三个 Hook 足够覆盖"入站、出站、规划"三层。

## 3. 总体架构

```
                 ┌──────────────────────────── MaiBot Host ────────────────────────────┐
 QQ 群消息 ──────▶│ adapter ─▶ SessionMessage ─▶ [Hook] chat.receive.before_process      │
                 │                                   │                                  │
                 │                         ┌─────────┴─────────┐                        │
                 │                    abort│                   │continue                │
                 │                         ▼                   ▼                        │
                 │                    丢弃（不入库）      HeartFlow / Maisaka 推理        │
                 │                                             │                        │
                 │                                   reply 工具生成回复                  │
                 │                                             ▼                        │
                 │                              [Hook] send_service.before_send          │
                 │                                   │              │                     │
                 │                              abort│              │send                 │
                 │                                   ▼              ▼                     │
                 │                              取消发送        Platform IO ──▶ QQ 群     │
                 └──────────────────────────────────────────────────────────────────────┘

 插件内部：
   IdentityResolver（名单 / 行为学习 / 昵称正则 / 自身账号）
        │
        ▼
   StreamGuard（per 群）: 滑动窗口指纹 + 链条计数 + 退避冷却 + 交替节奏
        │
        ├─▶ 入站判定 ──▶ abort / 放行
        ├─▶ 出站判定 ──▶ 取消发送 / 放行
        └─▶ 可选：frequency.set_adjust、planner 工具裁剪
```

代码分两层，刻意解耦：

- `loopguard_core.py`：纯标准库（`hashlib / unicodedata / re / dataclasses / collections`），零 SDK 依赖，可单独跑单元测试（含身份/频率/状态边界回归）。
- `plugin.py`：只做配置映射、身份识别、Hook 适配、状态落盘、命令（用 `tests/stubs/` 顶替 SDK 做 Hook 级回归）。

## 4. 身份识别：怎么知道对面是机器人

OneBot v11群消息标准没有通用的 is_bot 字段。v1.2将“真实身份”和“可疑行为”分开，未知默认放行，避免用@、昵称、一次引用直接定性。

1. 自身账号：识别本实例回声；随后真人白名单优先于其它身份来源。
2. 显式机器人名单：推荐主手段，准确性取决于部署者维护的名单。
3. 多轮行为学习：默认180秒内至少3轮回声、2种来源文本，其中至少2轮复述紧邻的已知bot内容；无已知bot锚点时需至少4轮、3种来源文本。
4. 每次回声双方正文至少12字、长度比≥0.65、来源间隔≤60秒；引用组件不属于本人正文。行为响应时间独立可配，覆盖慢模型。
5. 可选频率嫌疑：接话只看紧邻消息，并要求多次响应已知bot。按账号累计独立窗口，普通真人快速聊天仅提示嫌疑。
6. 昵称默认只作弱提示；显式开启 trust_name_patterns 才直接按bot处理；空列表关闭昵称提示，.*会匹配所有人。

自动学习只作用当前平台、当前聊天流，默认30分钟过期；足够证据的本条仍放行，下一条才应用bot规则。who展示来源和证据，forget清理学习及累计证据。v1旧学习数据不再沿用。

v1.3 增加两类更直接的信号和一条独立兜底：从宿主指定配置键读取受控bot名册；受控bot共享密钥可对群、账号、时间、原始正文做HMAC签名，入站严格校验后识别身份，适配器自带bot布尔扩展需显式信任。默认出站每流60秒最多6条，第7条静默120秒，仅明确的真人白名单清计数；该闸门独立于身份与复读相似度。短窗计数和冷却跨重载/重启保留，文本回声窗口仍不持久化。借鉴 [openclaw-napcat](https://github.com/Daiyimo/openclaw-napcat)、[Pallas-Bot的连接名册](https://github.com/PallasBot/Pallas-Bot/blob/main/pallas/core/platform/multi_bot/connected_roster.py) 和 [AstrBot多bot循环问题](https://github.com/AstrBotDevs/AstrBot/issues/10724)，以 [OneBot v11 群消息字段](https://github.com/botuniverse/onebot-11/blob/master/event/message.md) 为默认兼容基线。

这些规则是可解释启发式而非身份认证：真人也会复制、快速回复或长期对话bot。部署时需用演习日志和已标注样本评估误判/漏判；链条保护仅对已识别bot生效，明确身份优先配置名单。

## 5. 复读判定：信号与阈值

### 5.1 文本规范化

```
原始文本
  → unicodedata.normalize("NFKC")
  → 去 [CQ:...] 码、URL、@提及
  → 只保留 Unicode 类别 L（字母）与 N（数字），丢掉标点/空白/表情
  → 小写
  → 连续重复字符折叠（"啊啊啊啊" → "啊啊"）
  → 截断 400 字符
```

目的：让"同一句话换个 @、加个表情、改个标点"落回同一个指纹。规范化后为空（纯表情/纯标点）的消息**不参与查重**，直接放行——表情包对刷属于另一种玩法，本插件不接管。

### 5.2 指纹与相似度（三档，按代价递增）

| 档位 | 算法 | 阈值（默认） | 擅长 |
| --- | --- | --- | --- |
| 快 | BLAKE2b digest（规范化文本） | 完全相等 | 逐字复读，O(1) |
| 快 | SimHash 64 位 + 汉明距离 | ≤ 1 | 只认"几乎逐字相同"，作为便宜的预筛 |
| 准 | 2-gram Jaccard | ≥ 0.72 | 短句近义改写 |
| 准 | 2-gram 包含度 | ≥ 0.85 | "抄一遍再补几个字"——Jaccard 会被新增内容稀释，包含度不会 |

> 实测经验：中文短句上 SimHash 的汉明距离噪声很大（同义改写能到 10~20），所以插件里把它降级为"逐字重复的快速判定"，近义判定交给 2-gram 指标。这一取舍写在代码注释里，避免后来者把阈值调到 6 以上引入假阳性。
> 实测数据：`"今晚一起打游戏吗我这边随时可以"` vs `"今晚一起打游戏吗？我这边随时都可以！"` → Jaccard 0.81 / 包含度 0.93 / SimHash 距离 13；无关句子 Jaccard 0.00。

### 5.3 节奏信号（不依赖文本相似度）

有些复读是"内容不同但节奏成环"，纯文本比对抓不到，因此再加三个结构性信号：

| 信号 | 定义 | 默认阈值 |
| --- | --- | --- |
| `chain_limit` | 自最近一条人类消息起，连续机器人消息条数 | ≥ 4 条即静音 |
| `pingpong` | 回看最近 6 条全是机器人消息，且只涉及 2 个账号（交替接话） | 链条 ≥ 3 且命中交替 |
| `burst` | 60 秒内机器人消息条数 | ≥ 6 条算爆发，配合重复或接近上限时拦截 |

### 5.4 为什么不加语义相似度

- 成本：每次判定一次 embedding 调用，等于把省下来的 token 又花回去；本地模型则要求部署方额外装模型。
- 收益有限：`chain_limit` 与 `pingpong` 已经把"结构化成环"的场景兜住，语义改写通常也活不过 4 轮。
- 可解释性：部署者看到日志能立刻明白"因为第 4 条连续机器人消息"被拦，比"相似度 0.83"好排查。

如果确实需要，可以做**可选开关**：`ctx.llm.embed()` 已由 SDK 暴露，加一个 `semantic_threshold` 即可，但默认关闭。

## 6. 处置策略与状态机

### 6.1 判定优先级

对一条入站消息（`is_bot=True` 时）按顺序判定，命中即停：

```
1. self_echo        → 拦截，不计退避档位（自己的回声不是循环信号）
2. cooldown 生效中   → 拦截（reason=cooldown）
3. chain ≥ 4        → 拦截（chain_limit）
4. 内容重复 且 chain ≥ 2 → 拦截（duplicate）
5. 交替接话 且 chain ≥ 3 → 拦截（pingpong）
6. 爆发 且 (重复 或 chain ≥ 3) → 拦截（burst）
7. 其余             → 放行（allow_bot），并累计"允许的机器人消息"计数
```

设计意图：**第一次允许**。对面机器人说了一句正常的新内容，本实例可以正常回应一轮；只有进入"重复 / 交替 / 超长链条"才动手。这样既打断死循环，又不至于把群里的另一个机器人当空气。

### 6.2 指数退避

```
strike = min(strike + 1, 8)
cooldown = min(base × multiplier^(strike-1), max)
cooldown_until = max(cooldown_until, now) + cooldown
```

默认 `base=120s`、`multiplier=2`、`max=1800s`，即 120 → 240 → 480 → 960 → 1800 封顶。冷却期内同一聊天流的所有机器人消息都按 `cooldown` 拦截，且**不再叠加时长**（避免无限累加把群永久静音）。

人类发言（`is_bot=False`）触发 `observe_human()`：链条清零、冷却清零、退避档位 -1。这是"人类回到群里就把发言权还回去"的语义。

### 6.3 出站闸门

入站拦得再快，也拦不住"这一轮已经在推理、回复已经生成"的情况，所以 `send_service.before_send` 上做第二道检查：

- 冷却期内 → 取消本次发送；
- 正文与窗口内机器人消息、或与最近 10 条自己发出的内容重复 → 取消发送，并累加一次退避档位；
- 链条推进到上限（含本条）→ 取消发送（`chain_limit`）。

取消发送只影响这一次外发，不入库、不动记忆，下一轮照常判断。

> 关键细节：放行时这条回复**也要写入指纹窗口并推进链条**。本实例自己的发言同样是这条对话里的一条机器人消息；只统计"收到的"会让两只机器人各算一半链条，永远到不了上限——这一点在 `tools/loop_sim.py` 的场景 B 里能直接看到差异。

### 6.4 时序示例（两只机器人都装了插件）

```
t=0   人类：今晚有人开黑吗
t=2   Bot-A 收到（人类）→ 放行 → 回复
t=3   Bot-B 收到人类消息（放行）+ Bot-A 的消息（is_bot, chain=1, 不重复）→ 放行
t=6   Bot-A 收到 Bot-B 的消息（chain=2, 内容不同）→ 放行
t=9   Bot-A 收到 Bot-B 的第二条（chain=3, 与 Bot-B 上一条包含度 0.9）→ 拦截 duplicate
       → strike=1, cooldown=120s
t=9+  Bot-A 对之后所有机器人消息返回 cooldown，直到人类说话
```

净效果：一轮自然交互之后自动收敛，不会出现第三、第四轮。

## 7. 多实例仲裁（可选）

两只机器人都装上插件后，理论上都会在链条到 2~4 时收手。但如果两只的阈值配置不同，可能出现"A 已静音、B 还在说"的不对称。仲裁模式给出一个不需要通信的确定性规则：

- 配置 `[arbiter] peers = ["账号1","账号2"]`；
- 每个实例把 `peers + 自己` 按账号字符串排序，**字典序最小的实例为主实例**；
- 非主实例的阈值收紧：`max_chain_length - 1`、`duplicate_chain_threshold = 1`（任何重复立即退让）。

于是同一群里"谁先开口"是确定的，不会两个实例同时"礼让"到没人说话，也不会同时抢话。

## 8. 数据、性能与可观测性

| 项 | 设计 |
| --- | --- |
| 状态粒度 | 每个 `session_id` 一个 `StreamGuard`，`GuardRegistry` 最多保留 200 个流，按最后活跃时间淘汰 |
| 内存 | 每流最多 60 条指纹（每条含 16 字节 digest + 8 字节 simhash + 截断预览），单流约 20KB 上限 |
| 每消息开销 | 规范化 O(n) + 对窗口内 ≤60 条做 2-gram 比对；实测万级消息无压力，Hook 超时设 500ms 兜底 |
| 持久化 | `data/plugins/<plugin_id>/loopguard_state.json`：行为学习名单（带过期时间）、各流冷却状态、累计计数；30 秒脏写一次 + 卸载时落盘，临时文件原子替换 |
| 观测 | 每条拦截打一行 INFO：`stream / sender / reason / chain / cooldown / text[:60]`；`/loopguard` 命令看当前流快照 |
| 演习 | `plugin.dry_run = true`：判定照跑、日志照打，但一律放行——上线前用它观察 24 小时误杀 |

## 9. 灰度与回滚

1. **观察期（1 天）**：`dry_run = true`，只看日志里 `[dry-run] 本应拦截` 的条数与文本，确认没有把真人群友误判成机器人。
2. **小范围（1 个群）**：`dry_run = false`，`platform_scope = ["qq"]`，只在一只机器人上开，`notify_on_trip = true` 便于肉眼确认。
3. **全量**：两只机器人都装，打开 `[arbiter]`，`notify_on_trip = false`。
4. **回滚**：`/loopguard off`（进程内立即生效，配置不动）→ 或 WebUI 关 `plugin.enabled` → 或直接把插件目录移出 `plugins/`。

## 10. 失败模式与边界

| 场景 | 表现 | 处理 |
| --- | --- | --- |
| 名单漏登、昵称也不像机器人 | L3 行为学习在第一次复述时识破；若内容完全不同则可能放过 1~2 轮 | 由 `chain_limit` 兜底；长期建议补名单 |
| 真人群友复读玩梗 | 可能被判 duplicate | 只在 `is_bot=True` 时进入判定；纯表情/短文本（< 4 字符）不参与查重 |
| 另一只机器人没装插件 | 本实例静音，对方继续说话 | 单边也能显著降频（每次对方连发都会撞冷却）；建议两边都装 |
| Hook 超时或插件异常 | Host 按 `error_policy=SKIP` 记录并跳过，消息照常处理 | 三个 Hook 都声明了 SKIP + 500ms 超时，失败时退回原生行为 |
| 拦截后"记忆缺失" | 被拦的消息不在聊天历史里 | 有意为之：复读内容进上下文会让下一轮更像复读 |
| 多账号/多适配器 | `session_id` 已含 `account_id`/`scope` 维度 | 状态天然隔离，不会串流 |

## 11. 验收标准

| 编号 | 用例 | 期望 |
| --- | --- | --- |
| A1 | 两个机器人账号各发 4 条互不相同的内容，中间无人类发言 | 第 4 条起 `chain_limit` 拦截，日志可见 |
| A2 | 机器人 B 在 3 秒内复述机器人 A 的句子（改标点加表情） | B 的消息在 `before_process` 被拦，`reason=duplicate` |
| A3 | 人类插话后机器人再说话 | 链条归零、冷却清零，正常放行 |
| A4 | 本实例自己的回声消息 | `reason=self_echo`，不累加退避档位 |
| A5 | 已生成回复即将发送、此时处于冷却 | `before_send` 取消发送，`reason=cooldown` |
| A6 | 未登记账号逐字复述已知机器人 | 自动登记 + 拦截，日志出现"行为识别" |
| A7 | `dry_run = true` | 判定照跑、日志照打、消息全部放行 |
| A8 | 重启后 | 冷却状态与学习名单从 `loopguard_state.json` 恢复 |

核心判定由算法、身份/频率边界和Hook回归覆盖，当前共98项；无真实SDK时95项通过、3项Schema校验跳过。集成行为与真实群聊误判/漏判仍需按使用与部署文档验收，不把合成用例通过率等同真实识别准确率。

另有一个可复现的收敛模拟 `tools/loop_sim.py`（两只机器人各持一份守卫，无需 MaiBot 环境）：

```
场景 B：内容各异但节奏成环（两只机器人来回接话）
   1.0s  Bot-A 收 10000    放行            周末有什么安排吗
   2.0s  Bot-A 发 30001    放行            我打算去爬山，顺便拍点照片
   3.0s  Bot-B 发 30002    放行            爬山听起来不错，我可能去逛展
   4.0s  Bot-A 发 30001    放行            逛展也行，最近有几个摄影展
   4.5s  Bot-A 收 30002    拦截/chain_limit 摄影展我倒是没关注过，有推荐吗
   5.0s  Bot-B 发 30002    拦截/chain_limit 摄影展我倒是没关注过，有推荐吗
   5.5s  Bot-B 收 30001    拦截/cooldown    我回头整理一份清单发群里
```

第 4 条机器人消息处收敛，之后进入 120 秒冷却；场景 A（互相复述）在第 2 条就由 `duplicate` 拦下，场景 C 验证人类发言立即清零。

## 12. 后续可扩展

- WebUI 首页卡片：展示各群拦截计数与最近拦截原因（`@HomeCard` + `@API`）。
- 语义兜底：`semantic_threshold` 开关，接 `ctx.llm.embed()`。

- 与主程序共建：把"发送者是否机器人"提升为 `message_info.additional_config` 的标准字段，插件就不必再做 L3/L4 推断。
